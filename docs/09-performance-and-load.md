# Performance and Load (Phase 8 evidence)

Measured on 30 September 2026. Everything here can be re-run with the scripts in `scripts/perf/`; the procedure is at the end.

## Summary

| Question | Answer |
|---|---|
| Does the system carry 40 concurrent users? | **Yes.** 40 users for 3 minutes, 3,282 page loads, **0 errors**, median **132 ms**, 95th percentile **455 ms**. |
| Can 40 people sign in at the same moment? | **Yes**, after a fix: all 40 in **0.5 s** from one network address. Before the fix, 20 of 40 were refused. |
| Where is the ceiling? | One application process on the test laptop saturates at about **20 page loads per second**, still with 0 errors. |
| Largest defect found | The **Audit Log** page took **15–19 s** with 500,000 audit rows; now **132 ms**. |

## Test conditions

**Data.** A separate database, `nib_valuation_perf`, holding five years of work at production scale, generated by `scripts/perf/generate-volume.sql`:

| Table | Rows |
|---|---:|
| Valuation cases (2021–2025, 85% finished) | 50,000 |
| SLA records | 50,000 |
| Workflow history | 300,000 |
| Workflow tasks | 166,500 |
| Notifications | 400,000 |
| Audit log | 500,000 |
| Civil properties / vehicles | 30,000 / 30,000 |

**Users.** 40 signed-in sessions in the bank's proportions: 15 branch process owners, 12 valuators, 5 checkers, 5 managers, 2 directors and 1 administrator. Each follows its role's own pages (dashboard, task list, case page, valuation workspace, search, reports) and opens only cases in its own list.

**Pace.** Each user pauses 1–3 seconds between clicks. That is several times faster than people really work, so it is a heavy test, not a typical day.

**Machine.** One laptop: Intel Core Ultra 7 256V (8 threads), 16 GB, Node 24, PostgreSQL 18. The same machine was also running the development server, PostgreSQL and the load generator, so the figures are conservative for a dedicated server.

**Build.** The production build (`next build`, `next start`), with the production security policy in force.

## Results

### 40 users, 3 minutes, 1–3 s between clicks

| | Before tuning | After tuning |
|---|---:|---:|
| Page loads | 2,850 | 3,282 |
| Errors | 0 | 0 |
| Median | 421 ms | **132 ms** |
| 95th percentile | 1,146 ms | **455 ms** |
| 99th percentile | 1,712 ms | **818 ms** |

Per page after tuning (95th percentile): search 584 ms, valuation workspace 525 ms, case page 522 ms, civil register 471 ms, dashboard 441 ms, reports 413 ms, SLA register 404 ms, notifications 365 ms, request list 357 ms, task list 326 ms, audit log 288 ms.

### Stress: 40 users clicking without pause, 60 s

1,262 page loads, **0 errors**, 20.6 per second, median 1.5 s. This is the saturation point of one Node.js process on this laptop: beyond it, requests queue rather than fail.

### Morning sign-in rush: 40 sign-ins at once, one network address

| | Before | After |
|---|---|---|
| Signed in | 20 | **40** |
| Refused as "too many attempts" | 20 | 0 |
| Wall time | 2.6 s | 0.5 s |

## What was changed

| Finding | Cause | Fix |
|---|---|---|
| Audit Log page 15–19 s | Prisma's `distinct` read all 500,000 rows twice per page load to build the filter lists, and newest-first had no index | Filter lists walk the existing index one value at a time (6 ms); new index on `occurredAt` |
| Newest-first lists scanned 16,000–50,000 rows (20–80 ms each) | No index matched the sort | Indexes on notifications (recipient, created), cases (branch, created) and cases (department, created); migration `20260930060000_phase8_list_indexes` |
| Half of an office refused at sign-in | 20 attempts per address per 5 minutes; an office behind one proxy shares an address | Per-address limit is now a setting, `security.login_attempts_per_ip`, default 100. Per-account limits and lockout are unchanged |
| Client address could be forged | The *first* `X-Forwarded-For` entry was trusted, and the client writes it | The address is read from the entry appended by our own proxy (`TRUSTED_PROXY_HOPS`) |
| A session write on every request | The idle timeout was slid on every page load | At most once a minute per session |

Query plans before and after, measured on the perf data:

| Query | Before | After |
|---|---|---|
| Audit log, newest 50 | parallel sequential scan, 77 ms | index scan |
| Audit filter lists | 500,000 index entries, 360 ms (plus the in-memory work) | 7 index seeks, 6 ms |
| A user's notifications | 32,000 rows sorted, 18 ms | index scan |
| A branch's cases | sequential scan, 23 ms | index scan |
| The department's cases | parallel sequential scan, 44 ms | index scan |
| Search by owner name | trigram index, 10 ms | unchanged |
| Dashboard status counts | index-only scan, 2 ms | unchanged |
| A maker's open tasks | partial index, 0.1 ms | unchanged |

## Sizing recommendation

- **Application server:** 4 vCPU and 8 GB RAM, running **two** application processes behind the reverse proxy. One process carried the heavy test comfortably; two give headroom and let one restart while the other serves. Both must run **the same build** (see the runbook).
- **Database:** PostgreSQL 16 or later, 4 vCPU, 8 GB RAM, SSD. At this volume the database was never the bottleneck: the slowest remaining query takes 10 ms.
- **Connection pool:** `DATABASE_POOL_MAX=10` per process, 20 in total, well inside PostgreSQL's default 100.

## Known limits

- **Password hashing on locked-down Windows.** Where an application-control policy blocks the native Argon2 module, a WebAssembly implementation takes over automatically. It runs on the main thread, so a burst of sign-ins briefly delays other requests: 40 sign-ins took 0.5 s in total here. On Linux, or with the module allowed, the native module is used and runs off the main thread.
- **Per-process state.** The sign-in limiter and the configuration cache live in each process. With two processes, the limit per address is effectively doubled, which is acceptable. SLA sweeps may overlap across processes; each change is now claimed by exactly one sweep, so notifications are not duplicated (see the integration test).

## Re-running

```bash
# 1. A disposable database (the scripts refuse any name not ending in _perf)
createdb nib_valuation_perf
DATABASE_URL=postgresql://.../nib_valuation_perf npx prisma migrate deploy
DATABASE_URL=postgresql://.../nib_valuation_perf npx tsx prisma/seed/index.ts
psql -d nib_valuation_perf -v cases=50000 -f scripts/perf/generate-volume.sql

# 2. Sessions for 40 virtual users
DATABASE_URL=.../nib_valuation_perf PERF_PASSWORD='...' \
  npx tsx scripts/perf/prepare-sessions.mts sessions.json

# 3. A production build against the perf database
npx next build
DATABASE_URL=.../nib_valuation_perf APP_URL=http://localhost:3100 npx next start -p 3100

# 4. The runs
node scripts/perf/load-test.mjs --sessions sessions.json --duration 180 --think 1000-3000
node scripts/perf/load-test.mjs --sessions sessions.json --duration 60 --think 0-0
PERF_PASSWORD='...' node scripts/perf/login-storm.mjs --sessions sessions.json

# 5. Clean up
dropdb nib_valuation_perf
```
